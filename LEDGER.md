# Limitation ledger — evidence snapshot and open questions

This ledger distinguishes the user-run WSL verification batch (committed and inspected for integrity/content in this checkout) from Arena regeneration and from imported Track 1 evidence. The L3 paired PCAP checksums passed when verified from `results/l3_paired_batch/`; the batch JSON files parsed successfully. **The WSL execution was not independently regenerated in Arena.** Track 1 captures and analysis remain teammate-supplied/imported and provisional; see [`docs/track1-evidence-audit.md`](docs/track1-evidence-audit.md). The batch's exact-byte baseline uses TShark output from each same clean or mutated PCAP as its comparator—not independent ground truth.

| ID | Limitation question | Available evidence and exact numbers | Status / next validation |
|---|---|---|---|
| **L1** | Do reference tools expose QUIC v1 ClientHellos, and does the C++ extractor match under bounded impairments? | The WSL batch records TShark 4.6.4, GCC 15.2.0, OpenSSL 3.5.5, Python 3.14.4, WSL Linux 6.18.33.2; CTest **1/1**, pytest **39/39**. Two traces × six cases (baseline, reverse order, shuffle, drop one Initial-CRYPTO record, drop every third selected record, truncate a selected record by 64 bytes) report **54/54 exact-byte multiset matches** total, **0 misses / 0 extras**, recall 1.0 in every case. Per client: 27/27; for the every-third-drop case, TShark reports 2 and C++ matches 2 (not the five original hellos). Manifest: 16 capture records, 15 packet-bearing and one empty, all provisional. | **No broad extraction/reassembly gap demonstrated in these two traces and six conditions.** This is batch-artifact-inspected, user-run evidence, compared to TShark on the same mutated PCAPs; it is neither independent Arena reproduction nor proof of broad QUIC correctness. The baseline also exposes a narrower packet-accounting defect: Chromium has 16 client Initial records (10 decrypted, 6 failures); curl has 20 (10 decrypted, 10 failures), with the failures in five switched-DCID alias buckets per trace. A stateful association implementation and harness have been added, but post-change WSL results are pending. Do not claim increased ClientHello recall; existing complete extraction is 5/5 per clean trace. See `docs/quic/implementation-status.md` and the referenced batch artifacts. |
| **L2** | Which certificate/HTTP fingerprints require TLS secrets? | Imported `tls_keylog_curl` summary reports JA4X/JA4H count **0 without keys** and **5 with keys** for one TLS 1.3 sample. The key log is intentionally absent. | **Provisional, single sample.** The keyed arm cannot be regenerated from this repository. Do not commit session secrets; recapture a controlled session if needed. TLS 1.3 certificate and HTTPS application data are encrypted after ServerHello; ordinary TLS 1.2 certificate visibility differs. See `docs/landscape.md`. |
| **L3** | How do capture vantage and offload affect TCP fingerprint attribution? | The earlier offload-on/off PCAPs remain separate runs: each has 3 complete SYN/SYN-ACK streams and peer MSS 65495; they are not paired. A new committed user-run batch at `results/l3_paired_batch/` contains three sequential container requests and matching Windows Wi-Fi observations to `104.16.124.96:443`, paired by timestamp/order (TShark 4.6.4 analysis, raw PCAP SHA256 manifest passes). Container stream IDs 0/1/2 pair with Wi-Fi 17/18/19; every pair is classified `separate_tcp_legs_or_sequence_rewrite`, with distinct client and server ISNs/4-tuples and client profile MSS/WS/TTL 1460/10/64 vs 1460/8/128. Peer SYN-ACK profiles are 1460/7/63 vs 1400/13/52. This run does **not** contain MSS 65495. The WSL `eth0` PCAP is 188 B with two packets captured but zero SYN rows; vEthernet has 175 packets/eight SYN rows in four other streams but no matching probe tuple; bridge capture failed with “No such device”. | **A repeatable cross-vantage handshake difference is observed for three controlled requests; mechanism and fingerprint impact remain unproven.** The paired checker’s separate-leg/sequence-rewrite label is not proxy proof; the capture points do not locate the intermediary, Wi-Fi is a host-adapter capture, and no JA4T/JA4TS is calculated. Keep as a secondary limitation investigation. Do not say fields in one packet were rewritten, claim an OS misclassification, or transfer the offload MSS 65495 result to this paired run. See `docs/l3-contribution-plan.md` and `results/l3_paired_batch/`. |
| **L4** | How do PQ versus classic key-share settings affect ClientHello size and fingerprints? | Imported raw T4 output contains **5 ClientHellos per arm**. TShark `tls.handshake.length` values are **1511** (PQ `X25519MLKEM768`) and **508** (classic `X25519`); server-selected key-share groups are **4588** and **29**, respectively. JA4 values differ: `t13d3012h2_1d37bd780c83_7f037f8d6676` vs `t13d3014h2_1d37bd780c83_3eb322dd144c` (extension count and extension-derived hash differ; cipher component is the same). | **One client/environment, imported evidence.** This supports a size/group/fingerprint difference in this controlled sample; it does not show that JA4 directly encodes the selected group or generalize to all PQ clients. Do not conflate `tls.handshake.length` with complete wire bytes. See `docs/tests/T4_post_quantum.md`. |
| **L5** | How stable are fingerprints over repeats, and across clients sharing a TLS library? | Imported `tls_chromium_repeat` JSON contains **50 ClientHellos**, **50 distinct JA3**, and **15 distinct JA4** in the released-path raw output. Its 15 first signature-algorithm values are GREASE-pattern values (`0a0a` through `fafa`); this is consistent with GREASE variation contributing to the 15 outputs. The supplied summary reports **1** for FoxIO `ja4-main` commit `c6469a7…`, but those per-capture `ja4-main` records are not preserved. Imported curl and Python samples each have **10 hellos, 1 JA3 and 1 released-path JA4**. | **Release/source-path discrepancy is suggestive, not independently reproduced.** The committed raw fields support the GREASE correlation; exact executable/source provenance and the `ja4-main` count cannot be recomputed from its absent raw output. This is not evidence that all JA4 implementations are unstable and is not a novel contribution (reported fix is upstream). See `docs/tests/T5_stability.md` and `docs/track1-evidence-audit.md`. |
| **L6** | Does IPv6 change TLS/TCP fingerprint observations? | `tls_ipv6.pcap` is a **24-byte** PCAP global header with **zero packet records**. The audited summary marks two empty outputs **not comparable**, not agreement. | **Not measured.** Repeat on a network with IPv6, verify packet presence, and then compare. |
| **L7** | How do ECH and encrypted DNS affect site-name attribution? | Imported ECH-off and ECH-on PCAP JSON each contain **5 ClientHellos**. The target `crypto.cloudflare.com` appears in **2** ECH-off outer-SNI rows; the ECH-on outer name appears as `cloudflare-ech.com` in **2** rows. Team-supplied page output reports `sni=plaintext` with ECH off and `sni=encrypted` with ECH on. The imported report says plaintext DNS still exposed `crypto.cloudflare.com` in both arms. The ECH+DoH PCAP JSON has **12** ClientHellos, all with outer SNI `cloudflare-dns.com`, but the saved target-page output is empty. | ECH off/on is a **team-supplied one-run observation** consistent with outer-name protection. The ECH+DoH target page is **incomplete/unverified**; 12 ClientHellos to the DoH hostname do not prove the intended page loaded or that the DoH arm succeeded. Separate target traffic from Chromium background connections; repeat on a network that permits DoH. Do not claim no DNS leakage or broad privacy guarantees. See `docs/tests/T7_ech_dns.md` and `results/track1/page-observations.md`. |

A TLS 1.3 certificate-compression/abridging scenario remains a watch item, not one of the seven measured rows. Do not label simulations as observed traffic.

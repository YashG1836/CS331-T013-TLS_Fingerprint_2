# Limitation ledger — evidence snapshot and open questions

This ledger distinguishes the user-run WSL verification batch (committed and inspected for integrity/content in this checkout) from Arena regeneration and from imported Track 1 evidence. The WSL batch manifest passed SHA-256 verification from the repository root; the referenced JSON files parsed successfully. **The batch execution was not independently regenerated in Arena.** Track 1 captures and analysis remain teammate-supplied/imported and provisional; see [`docs/track1-evidence-audit.md`](docs/track1-evidence-audit.md). The batch's exact-byte baseline uses TShark output from each same clean or mutated PCAP as its comparator—not independent ground truth.

| ID | Limitation question | Available evidence and exact numbers | Status / next validation |
|---|---|---|---|
| **L1** | Do reference tools expose QUIC v1 ClientHellos, and does the C++ extractor match under bounded impairments? | The WSL batch records TShark 4.6.4, GCC 15.2.0, OpenSSL 3.5.5, Python 3.14.4, WSL Linux 6.18.33.2; CTest **1/1**, pytest **39/39**. Two traces × six cases (baseline, reverse order, shuffle, drop one Initial-CRYPTO record, drop every third selected record, truncate a selected record by 64 bytes) report **54/54 exact-byte multiset matches** total, **0 misses / 0 extras**, recall 1.0 in every case. Per client: 27/27; for the every-third-drop case, TShark reports 2 and C++ matches 2 (not the five original hellos). Manifest: 16 capture records, 15 packet-bearing and one empty, all provisional. | **No extraction/reassembly gap demonstrated in these two traces and six conditions.** This is batch-artifact-inspected, user-run evidence, compared to TShark on the same mutated PCAPs; it is neither independent Arena reproduction nor proof of broad QUIC correctness. Batch outputs also show incomplete-flow/decrypt-failure dispositions; these do not contradict matching all complete TShark ClientHellos. Do not claim QUIC reassembly as the original contribution. The header inventory explains five post-switch client-DCID failure buckets per trace; they are not server-direction attempts. See `docs/quic/implementation-status.md` and `results/track2/verification-batch-20261104-201936/`. |
| **L2** | Which certificate/HTTP fingerprints require TLS secrets? | Imported `tls_keylog_curl` summary reports JA4X/JA4H count **0 without keys** and **5 with keys** for one TLS 1.3 sample. Do not commit session secrets; recapture a controlled session if needed. TLS 1.3 certificate and HTTPS application data are encrypted after ServerHello; ordinary TLS 1.2 certificate visibility differs. See `docs/landscape.md`. |
| **L3** | How do capture vantage and offload affect TCP fingerprint attribution? | The batch SYN analyzer used TShark 4.6.4 on two separate imported PCAPs. Each has **3 complete SYN/SYN-ACK streams** (6 SYN observations). Every client SYN is MSS/window-scale/window/TTL **1460/10/64240/64**; every peer SYN-ACK is **65495/7/65408/63**. IP length **60 B**, frame length **74 B** for each; same-capture option differences: MSS, window scale, window. Source capture client is `172.17.0.2`, peer `104.16.124.96`. The analyzer explicitly says not to infer a proxy from one capture. Separately, a user-reported controlled container probe had peer MSS **1460** and did not appear on WSL `eth0`. | **Primary candidate to investigate, not a finding or demonstrated proxy detector.** `65495` is a possible advertised MSS value, not impossible, a measured path MTU, or proof of TCP termination. The two captures are not paired vantage points. WSL `eth0` is not the outer observation point for the separate reported probe; the Windows/host-side leg is still unobserved. Obtain synchronized captures across a known boundary, distinguish NAT from termination, correlate both TCP legs, repeat, and keep TSO/GSO independent. See `docs/l3-contribution-plan.md`. |
| **L4** | How do PQ versus classic key-share settings affect ClientHello size and fingerprints? | Imported raw T4 output contains **5 ClientHellos per arm**. TShark `tls.handshake.length` values are **1511** (PQ `X25519MLKEM768`) and **508** (classic `X25519`); server-selected key-share groups are **4588** and **29**, respectively. Do not conflate `tls.handshake.length` with complete wire bytes. See `docs/tests/T4_post_quantum.md`. |
| **L5** | How stable are fingerprints over repeats, and across clients sharing a TLS library? | Imported `tls_chromium_repeat` JSON contains **50 ClientHellos**, **50 distinct JA3**, and **15 distinct JA4** in the released-path raw output. The supplied summary reports **1** for FoxIO `ja4-main` commit `c6469a7…`, but those per-capture `ja4-main` records are not preserved. The audited summary marks two empty outputs **not comparable**, not agreement. | **Not measured.** Repeat on a network with IPv6, verify packet presence, and then compare. |
| **L7** | How do ECH and encrypted DNS affect site-name attribution? | Imported ECH-off and ECH-on PCAP JSON each contain **5 ClientHellos**. The target `crypto.cloudflare.com` appears in **2** ECH-off outer-SNI rows; the ECH-on outer name appears as `cloudflare-ech.com` in **2** rows. Team-supplied page output reports `sni=plaintext` with ECH off and `sni=encrypted` with ECH on. The imported report says plaintext DNS still exposed `crypto.cloudflare.com` in both arms. The ECH+DoH PCAP JSON has **12** ClientHellos, all with outer SNI `cloudflare-dns.com`, but the saved target-page output is empty. | ECH off/on is a **team-supplied one-run observation** consistent with outer-name protection. The ECH+DoH target page is **incomplete/unverified**; 12 ClientHellos to the DoH hostname do not prove the intended page loaded or that the DoH arm succeeded. Separate target traffic from Chromium background connections; repeat on a network that permits DoH. Do not claim no DNS leakage or broad privacy guarantees. See `docs/tests/T7_ech_dns.md` and `results/track1/page-observations.md`. |

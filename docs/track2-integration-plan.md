# Track 2 integration plan: real QUIC captures into the modular C++ core

## Objective

Connect the existing modular extractor to Yash's `quic_chromium.pcap` and `quic_curl.pcap`, retaining the current boundaries: `packet_parser`, `initial_crypto`, `frame_parser`, `crypto_reassembly`, and `client_hello`. The imported TShark summaries report five ClientHellos for each capture and up to 21 CRYPTO fragments in Chromium. They are teammate-supplied evidence, not outputs independently rerun with TShark in this environment.

## Implementation status and gates

1. **PCAP input adapter — implemented and locally tested.** `capture_reader` reads classic PCAP v2.x, Ethernet link type 1, and UDP payloads in unfragmented IPv4/IPv6. It rejects PCAPNG and non-Ethernet link types, and explicitly counts unsupported VLAN, fragment, and IPv6 extension-header cases. No libpcap dependency was added. The synthetic C++ test covers an IPv4/UDP frame and PCAPNG rejection; more malformed/truncated and IPv6 fixtures remain useful.
2. **Flow and Initial handling — first end-to-end slice works, not a complete flow model.** The CLI examines destination-port 443 datagrams, parses coalesced long-header packets, and derives v1 client Initial keys. It currently groups by DCID and tracks the largest recovered packet number per DCID. This is adequate for the imported examples but does not yet model both directions, address/port tuples, DCID changes, migration, or multiple packet-number spaces comprehensively.
3. **Cross-datagram CRYPTO reassembly — exercised on both imported captures.** Decrypted Initial CRYPTO frames are inserted into the existing offset-aware reassembler. The CLI reports per-DCID decrypt, frame, reassembly, and completeness counts. Each capture yielded five complete ClientHellos; five other candidate DCIDs in each produced decrypt failures and remain unresolved rather than being silently counted as recovered.
4. **Reference comparison — extent/framing checked; byte-for-byte comparison is still open.** For both captures, recovered handshake counts and total lengths match the imported TShark `tls.handshake.length` values plus the four-byte TLS handshake header. Every recovered byte sequence has a valid ClientHello handshake type and a declared body length consistent with its actual size. However, the saved TShark JSON contains summaries and lengths, not full ClientHello bytes, and TShark is unavailable here. Therefore this is **not** an exact-byte comparison against an independent raw reference. JA3/JA4 values are not generated by this C++ CLI.
5. **Tests and runs — default suites pass.** A synthetic classic-PCAP test now runs in the lightweight C++ test executable. CTest passes 1/1 and pytest passes 20/20. The CLI also runs successfully against both imported QUIC captures. These results validate the current code path, but do not independently rerun the imported TShark/FoxIO outputs.

Fresh CLI output is stored locally (the full hex logs are Git-ignored) in `results/reproduced/quic_chromium_extractor.txt` and `results/reproduced/quic_curl_extractor.txt`. The tracked machine-readable length/framing check is `results/quic-extractor-comparison.json`; see `results/verification-status.md` for interpretation and limits.

## Candidate original contribution (not yet a claim)

The best-aligned candidate remains a **capture-quality-aware QUIC Initial recovery pipeline**: flow-aware CRYPTO reconstruction plus explicit completeness/loss diagnostics and byte-level cross-validation. Current measurements show recovery on the imported captures but do not yet establish a novelty claim or robust behavior under controlled packet loss, reordering, truncation, or changing connection IDs. Measure those cases on controlled copies of the captures and compare exact bytes against a trusted reference before claiming the contribution.

This is a candidate engineering/research contribution, not yet proven novel. Before calling it the required original contribution, check related QUIC dissectors and obtain team/course approval. T5's reported 15-to-1 JA4 change is already fixed in unreleased upstream code; T3's proxy/MSS narrative conflicts with the saved aggregate metrics. Neither is currently a clean novelty claim. A JA4T/MSS proxy-sanity tool remains an alternative only after its T3 evidence is reconciled and a comparison baseline is selected.

## Reproduction commands

Build and run the local core and extractor (paths below reflect the integration sandbox's temporary CMake/OpenSSL setup; normal Ubuntu installations can omit the environment prefixes):

```sh
PATH="/tmp/cn-zip-venv/bin:$PATH" CMAKE_PREFIX_PATH=/tmp/cn-openssl-build cmake --build build -j2
PATH="/tmp/cn-zip-venv/bin:$PATH" ctest --test-dir build --output-on-failure
python3 -m pytest -q
build/code/quic/src/quic-fingerprint --pcap captures/pcaps/quic_chromium.pcap > results/reproduced/quic_chromium_extractor.txt
build/code/quic/src/quic-fingerprint --pcap captures/pcaps/quic_curl.pcap > results/reproduced/quic_curl_extractor.txt
```

To obtain an independent raw reference in an Ubuntu environment with Wireshark/TShark installed, run:

```sh
tshark -r captures/pcaps/quic_chromium.pcap -Y 'tls.handshake.type == 1' -T jsonraw > /tmp/quic_chromium-clienthellos.json
tshark -r captures/pcaps/quic_curl.pcap -Y 'tls.handshake.type == 1' -T jsonraw > /tmp/quic_curl-clienthellos.json
```

Inspect whether the installed TShark's `jsonraw` export retains the handshake byte ranges needed for exact comparison; if it does not, use a decoder/export path that emits the full reassembled TLS handshake bytes. Compare each ClientHello in capture order by bytes, not merely by digest or total length. Keep raw exports outside Git unless the team explicitly wants them as curated evidence; they may contain network identifiers. Docker and TShark are unavailable in the integration environment, so these independent reference runs have not been performed here.

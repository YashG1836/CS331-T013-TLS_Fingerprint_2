# Track 2 integration and validation plan

## Objective

Connect the modular C++ QUIC v1 core to Yash's `quic_chromium.pcap` and `quic_curl.pcap`, preserving the existing boundaries: `packet_parser`, `initial_crypto`, `frame_parser`, `crypto_reassembly`, and `client_hello`.

## Implementation and evidence status

1. **PCAP adapter — implemented.** `capture_reader` reads classic PCAP v2.x, Ethernet link type 1, and UDP payloads in unfragmented IPv4/IPv6. It rejects PCAPNG and non-Ethernet link types, and reports unsupported VLAN, fragment, and IPv6 extension-header cases. No libpcap dependency was added. The synthetic C++ test covers IPv4/UDP and PCAPNG-magic rejection; more malformed/truncated and IPv6 fixtures remain useful.
2. **Initial handling — legacy mode plus bounded stateful mode.** Legacy PCAP mode remains available and groups client Initial state by current DCID. The new `--stateful-initial-context` mode parses source/destination IPv4/IPv6 endpoints, normalizes client/server direction on a UDP 4-tuple, retains the original client Initial DCID, learns server Initial SCIDs as aliases, and keeps separate client/server Initial packet-number contexts. Retry, migration, tuple reuse, and PCAPNG remain unsupported.
3. **CRYPTO reassembly, incomplete diagnostics, and DCID limitation.** Both modes feed decrypted client Initial CRYPTO frames to the offset-aware reassembler and report completeness/missing ranges. The stateful mode adds directional and per-connection packet/decrypt/failure/context-miss counters, plus separate switched alias bucket and switched packet counts. It also re-runs DCID-keyed client accounting alongside the stateful result. The committed inventory classifies the old five extra failure buckets per trace as client Initials whose DCID equals a server Initial SCID; RFC 9001 §5.2 keeps the original Initial secret context. The user reports positive post-change WSL client counts; server-direction metrics and the explicit byte comparison are not included in the supplied summary. See `docs/quic/implementation-status.md`.
4. **Clean and impaired comparison — WSL batch artifacts committed.** The user-run batch at `results/track2/verification-batch-20261104-201936/` records TShark 4.6.4, GCC 15.2.0, OpenSSL 3.5.5, CTest 1/1, and pytest 39/39. Its six cases per trace report exact-byte multiset equality: 27/27 for Chromium, 27/27 for curl; 54/54 total, zero misses/extras. The every-third-drop case is 2/2 per trace against TShark on the same damaged variant. Artifacts and hashes were inspected in this checkout, but the WSL run was not regenerated in Arena and TShark is not independent ground truth. The separate earlier `tls.handshake_raw` export/script is not retained as a standalone artifact.
5. **Incomplete diagnostics and DCID context.** Batch impairment artifacts and JSON are present. A separate baseline-assisted diagnostic audit reports three incomplete statuses per trace; curl has no missing suffix beyond observed extent, while Chromium has a baseline-relative suffix `[1026,1891)` beyond the damaged capture's 1026-byte observed extent. Unknown expected length is correctly not inferred from damaged data. The header inventory identifies five later client Initial DCIDs per trace matching a server Initial SCID; these are post-switch client packets, not server-direction decrypt attempts. See `docs/quic/implementation-status.md` and `results/verification-status.md`.

## L1 interpretation

The clean and bounded impaired captures do not show a QUIC v1 ClientHello extraction gap relative to TShark: the committed user-run batch reports 54/54 byte-identical reference outputs across two traces and six cases. This closes only those comparator checks, not broad support under impaired capture conditions or independent ground truth. JA3/JA4 generation and full Track 1 tool reproduction remain separate.

## Current contribution direction and next checks

Broad QUIC Initial recovery/completeness diagnostics remain unsupported as a contribution by the tested stateless matrix: the complete ClientHello bytes already match TShark. A narrower packet-level association/accounting result is now primary. The committed 5 November WSL batch at `results/track2/verification-batch-20261105-105416/` records CTest 1/1, pytest 52/52, client decrypt improvements from 10/20→20/20 for curl and 10/16→16/16 for Chromium, all five server Initials decrypted per trace, zero baseline context misses, and exact 5/5 baseline ClientHello byte-multiset matches against TShark 4.6.4. The logs and per-connection/directional rows are archived and inspected here; the run was not independently reproduced in Arena. Stateful reverse/shuffle variants match 0/5 and 4/5 respectively per trace, so the no-regression result is limited to original captured order. Do not imply TShark failure or increased ClientHello recall.

**Secondary limitation investigation: L3 capture-vantage attribution.** The latest user-run batch manually correlates three container SYNs to three Wi-Fi adapter observations, with distinct tuples/ISNs and timing within 3-10 ms. The bridge capture failed; WSL `eth0` and vEthernet have no matching probe SYN tuple. This shows an observed difference across two points, but not proxy identity, exact termination mechanism, or JA4T/JA4TS error. Keep the old offload captures separate and do not transfer MSS 65495 to the paired run. See [`l3-contribution-plan.md`](l3-contribution-plan.md); prior-art and rubric review remain open.

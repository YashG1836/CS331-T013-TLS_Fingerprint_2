## 1. Hybrid implementation: C++20 protocol core; Python experiment harness

The working architecture follows the implementation plan's hybrid boundary. C++20 owns the bounded QUIC protocol/data path; Python owns experiment orchestration and evidence evaluation. This is a fit-for-task decision, not a claim that C++ is inherently faster, safer, or more correct than Python. No performance claim is made without a benchmark.

| Area | Working decision | Why and boundary |
|---|---|---|
| QUIC packet/UDP parsing | C++20 | Explicit bounded byte views and length arithmetic suit protected binary headers, packet boundaries, and malformed-input handling. The current adapter supports classic PCAP v2 Ethernet and unfragmented IPv4/IPv6 UDP; unsupported link/IP forms must fail visibly. |
| Initial cryptography | OpenSSL 3 APIs called from C++ | Use library HKDF, AES header-protection, and AEAD operations; do not implement cryptographic primitives. RFC vectors and capture-level comparisons are separate evidence. |
| Frames, CRYPTO reassembly, TLS structure | C++20 | Keep frame boundaries, CRYPTO offsets/overlaps, allocation limits, and nested TLS lengths explicit and unit-testable. Reassemble by CRYPTO offset, not packet arrival order. |
| Experiment harness and report values | Python | Validate JSON manifests, invoke pinned tools, build deterministic mutations, parse outputs, calculate metrics, and generate tables. Avoid rewriting protocol processing in Python or copying measurements manually into reports. |
| Python/runtime pin | WSL QUIC evidence: Python 3.14.4, GCC 15.2.0, OpenSSL 3.5.5, TShark 4.6.4. | These are the versions recorded by the committed 5 November QUIC batch. The plan's generic Python 3.12 target was not the runtime used for that evidence; keep actual experiment environments explicit and do not imply a 3.12 test. |
| JA4 construction | Use a verified reference first; no custom JA4 emitted by this prototype | Avoid a convenience reimplementation. Before any QUIC JA4 result, verify the QUIC transport marker and field construction against the pinned specification and an independent reference, comparing fields as well as final output. |
| Reference tools / environment separation | WSL QUIC comparison: TShark 4.6.4. Docker `cn-lab`: TShark 4.4.19; FoxIO `ja4` built from tag `v0.18.6` reports 0.18.5, while `ja4-main` commit `c6469a7` reports 0.18.6. | Keep these environments and outputs distinct. FoxIO's Rust CLI invokes TShark, so agreement is not independent packet-decoder evidence. Pin the source/tag, binary-reported version, tool command, and environment; a version alone does not prove support for the behavior being claimed. |
| Build, tests, CI | CMake, CTest, the lightweight C++ runner in `code/quic/tests/test_core.cpp`, pytest, GitHub Actions | The team chooses a zero-dependency C++ test runner rather than GoogleTest to avoid external build bloat and keep compilation fast and self-contained. Keep the CTest target and pytest suite; no GoogleTest migration is planned unless the team revisits this decision. |
| Corpus and generated results | JSON manifest; generated CSV/JSON/tables | Connect every capture to provenance, conditions, commands, versions, and report use. Source captures remain immutable; generate mutations and unreviewed reproduction outputs under `results/reproduced/`. |
| Capture and secrets | tcpdump/dumpcap where available; record vantage and conditions; keep key logs local by default | Capture interface, direction, offload, MTU, NAT/proxy conditions, and start/stop matter. Do not commit public-session secrets or represent a simulation as observed traffic. |

The reason for the language split is the task boundary: packet parsing and reassembly require explicit control over binary inputs and resource bounds; the experiment loop is mostly process orchestration, evidence bookkeeping, and statistics. Neither language choice proves correctness; independent protocol vectors, tests, and same-input comparisons remain necessary. The project does not add a libpcap dependency.

The current QUIC scope is deliberately limited to v1 Initial processing and the supported frame subset. PCAPNG, VLANs, IP fragments, IPv6 extension chains, QUIC v2, Retry transitions, tuple migration/NAT rebinding, 0-RTT decryption, all QUIC frame types, and JA4 calculation remain unsupported or unimplemented. The stateful Initial-context path is a fixed-4-tuple association model, not a complete connection tracker. C++20, modularity, and RFC-defined Initial decryption alone are not an original contribution.

The WSL verification batch at `results/track2/verification-batch-20261104-201936/` records GCC 15.2.0, OpenSSL 3.5.5, TShark 4.6.4, Linux 6.18.33.2 WSL2, CTest 1/1, and pytest 39/39. The batch is user-run evidence: its manifest hashes and JSON structure were checked in this checkout, but the WSL run was not independently regenerated here. The RFC 9001 Initial key test vector remains a separate unit test from capture-level evidence.

## 2. Keep broad QUIC recovery rejected; test the narrower Initial-context accounting defect

The batch evaluates six cases for each of two captures: baseline, reversed packet-record order, fixed-seed shuffle, one selected Initial-CRYPTO record dropped, every third selected Initial-CRYPTO record dropped, and a selected record truncated by 64 captured bytes. For each client, all six comparisons report exact-byte multiset equality with TShark's ClientHello bytes from that same case: 27/27 reference ClientHellos matched, with 0 misses and 0 extras. The every-third-drop case has 2 references and 2 matches, not recovery of the five original hellos. Aggregated: 54/54 reference outputs matched across 12 run-cases. These are batch-artifact-inspected results from a user-run WSL execution, not independent Arena reproduction or external ground truth; TShark is the comparator, and the comparison is conditioned on what TShark emits from each mutated PCAP.

The extractor's incomplete-flow and Initial decryption-failure statuses must not be conflated with a missed complete ClientHello: the measured comparison found no missing complete TShark output under these tested conditions. The evidence still rejects a broad extraction/reassembly contribution. A narrower packet-accounting defect is measured in the legacy logs: Chromium has 16 client Initial records, 10 successful and 6 failed; curl has 20, 10 successful and 10 failed. The failures lie in five switched-DCID alias buckets per trace, not five lost ClientHellos.

RFC 9001 §5.2 derives Initial secrets from the original client Initial DCID (subject to the Retry transition); the prototype's former per-packet implementation instead keyed each packet using its current DCID. The bounded stateful associator preserves the original DCID on the direction-normalized UDP 4-tuple, learns server Initial SCIDs, and maintains separate client/server packet-number contexts. The committed WSL verification batch `results/track2/verification-batch-20261105-105416/` was run against code commit `fa9fcdb` and is now inspectable in the checkout. It records a clean build, CTest 1/1, pytest 52/52, TShark 4.6.4, the exact baseline byte-multiset comparisons, and per-direction/per-connection accounting.

| Trace | Client Initial packets | Legacy DCID-keyed client decrypted / failed | Switched aliases / client packets using aliases | Stateful client decrypted / failed | Stateful server Initial decrypted / failed | Baseline ClientHello byte match vs TShark |
|---|---:|---:|---:|---:|---:|---:|
| curl | 20 | 10 / 10 | 5 / 10 | 20 / 0 | 5 / 0 | 5/5, multiset equal |
| Chromium | 16 | 10 / 6 | 5 / 6 | 16 / 0 | 5 / 0 | 5/5, multiset equal |

Each trace has five observed 4-tuple associations; baseline context-miss counts are zero in both directions. The measured delta is +10 decrypted curl client Initial packets and +6 Chromium packets. These are packet-accounting changes, not increased ClientHello recall. The baseline TShark byte comparison uses the same captured-order PCAP and matches all five complete ClientHellos in each trace by byte multiset, with zero misses/extras.

The stateful impairment results show an important order-dependence: in each trace, reverse-record-order gives 0/5 matched hellos, and shuffle gives 4/5; baseline, drop-one, every-third-drop, and truncation cases match the TShark outputs for those cases (5/5, 5/5, 2/2, and 5/5 respectively). Therefore “no recall regression” is supported only for the captured-order baseline, not reordered traces. The earlier stateless matrix remains 27/27 per trace across its six cases.

The causal boundary is the prototype's single-pass input-record processing, not QUIC semantics or a TShark failure. The first client Initial observed for a direction-normalized UDP 4-tuple seeds the context's presumed original DCID. A server SCID alias is added only after the corresponding server Initial is observed and associated with a previously observed client SCID. In the reversed-record batch, later client Initials using switched DCIDs occur before that server alias announcement and before the true first client Initial; the first switched DCID is consequently used as the provisional original-DCID context. The parser neither buffers unresolved packets nor reorders by timestamp, so subsequent packets cannot be associated with the required context in this pass. This explains the observed 0/5 reverse result; the fixed-seed shuffle retains enough context for 4/5. A timestamp-aware pre-pass or bounded buffering/deferred association could address this, but neither is implemented. These are tested mutation outcomes, not claims about every out-of-order capture.

Baseline ClientHello recall does not increase: both the earlier stateless path and stateful path emit 5/5 complete ClientHellos on each original-order trace, with exact-byte multiset parity against TShark 4.6.4. The user's supplemental frame audit reports that each complete ClientHello was already wholly present in pre-switch datagrams in these two captures, so the additionally accounted-for packets contain no bytes needed to complete those particular ClientHellos. That frame-level audit is user-reported and not yet archived in the batch; keep it labeled accordingly until packet/frame evidence is committed. The stateful change is packet-level accounting correctness and could protect extraction when handshake bytes span later datagrams, but these traces do not demonstrate a recall increase.

For the same reason, distinguish the prototype's legacy stateless accounting from the reference dissector: the user's separate WSL check reports that `tshark -r <capture> -Y 'quic.long.packet_type == 0 && quic.decryption_failed'` returned zero matching rows on each original curl/Chromium capture, including post-switch DCIDs. The exact filter output is not in the committed batch, so this remains user-reported supplemental evidence. TShark/Wireshark is treated as a stateful reference implementation/comparator, not an independent ground-truth oracle; do not describe the 16 prototype-baseline failures as Wireshark failures.

The academic scope is deliberately narrow. CID mechanics are specified by RFC 9000 §7.2 and Initial-key context by RFC 9001 §5.2; maintaining connection/CID state is established practice in full QUIC implementations and stateful analyzers (for example, [Google QUICHE](https://github.com/google/quiche), [ngtcp2](https://github.com/ngtcp2/ngtcp2), and [Wireshark](https://github.com/wireshark/wireshark)). We do not claim that stateful CID tracking itself is globally novel. The project evaluates a minimal stateless-to-stateful transition for lightweight passive streaming fingerprinting, using a fixed-tuple Initial associator to measure packet-accounting effects and ordering limits. This is the adopted project-level engineering/evaluation contribution, not a claim that CID association is a novel QUIC protocol mechanism. Targeted prior-art and course-rubric review remain necessary to establish how the course evaluates the contribution.

Known limitations and future work: Retry remains unsupported (`retry_packets_observed_unsupported`), as do migration/rebinding, QUIC v2, and order-robust deferred association. Future work is to add Retry integrity/key-transition vectors and captures, then test bounded buffering or a timestamp-aware discovery pass for out-of-order records. None of these capabilities should be implied by the current results.

The seven-row artifact audit marks L1/L2/L3/L4/L5/L7 PASS and L6 NOT_MEASURED for public IPv6 egress. This L6 scope is accepted: the attempted local `::1` loopback control produced no packet-bearing IPv6 PCAP and is not a substitute for public egress; public IPv6 remains unmeasured. Overall live status is therefore FAIL, not a public IPv6 pass. The evidence is archived, but independent clean-clone reproduction and course-rubric review remain open. Key citations: `results/track2/verification-batch-20261105-105416/quic-stateful/curl/impairment-results.json`, `results/track2/verification-batch-20261105-105416/quic-stateful/chromium/impairment-results.json`, `results/track2/verification-batch-20261105-105416/seven-rows-live.json`, `results/track2/verification-batch-20261105-105416/make-test.log`, and `results/track2/verification-batch-20261105-105416/environment.txt`; see also `docs/quic/implementation-status.md` and `results/verification-status.md`.

## 3. Treat L3 capture-vantage attribution as a candidate question, not a proxy finding

The earlier TSO/GSO-on/off captures remain separate single-vantage runs: each has three complete streams with client profile MSS/window-scale/window/TTL `1460/10/64240/64` and peer `65495/7/65408/63`. They are not paired and do not establish termination. A later committed user-run batch contains three manual timing-correlated container/Wi-Fi probe pairs to `104.16.124.96:443`; each is classified `separate_tcp_legs_or_sequence_rewrite`, with distinct tuples and initial sequence numbers. Container client MSS/WS/TTL is `1460/10/64` versus Wi-Fi `1460/8/128`; peer SYN-ACK is `1460/7/63` versus `1400/13/52`. MSS 65495 does not occur in this paired run.

The WSL `eth0` capture is 188 bytes with two packets captured but zero parsed SYN rows. vEthernet has 175 packets and eight SYN observations across four unrelated streams, not the controlled target tuple. The bridge capture failed because the named interface did not exist. Wi-Fi is an adapter capture, not a physical-wire tap. These results show a cross-vantage handshake difference for the three controlled requests but do not locate an intermediate mechanism, prove a proxy, calculate JA4T/JA4TS, or show OS misclassification. L3 is secondary, not the active primary candidate. Keep MSS 65495 scoped to the earlier offload captures and see `docs/l3-contribution-plan.md` for pair IDs and provenance.

## 4. Interpret post-switch QUIC DCIDs under the Initial key schedule, not as direction failures

Five later client Initial DCID buckets in each imported QUIC trace use a DCID equal to a server Initial SCID. These are client-to-server records, not server-direction attempts. The baseline stateful run now shows the narrow fix in the prototype's accounting: it decrypts all 20 curl and 16 Chromium client Initial packets with zero failures, while the prior DCID-keyed accounting reports 10/10 and 10/6 success/failure. All five server Initial packets per trace decrypt, and baseline context misses are zero. This aligns the measured packet-key association with RFC 9001 §5.2's original-DCID key derivation for these fixed-tuple captures; it does not establish full RFC 9001 compliance, Retry handling, migration support, or order-independent initialization. See [RFC 9001 §5.2](https://www.rfc-editor.org/rfc/rfc9001.html#section-5.2), [RFC 9000 §7.2](https://www.rfc-editor.org/rfc/rfc9000.html#section-7.2), and `results/track2/verification-batch-20261105-105416/quic-stateful/`.

## 6. Implementation-plan decisions, status, and open gates

This section records the current plan-aligned working decisions and known deviations so that the rationale is visible in one place. The implementation plan is an execution baseline, not proof that a gate has passed. This repository record remains provisional; changes to the approved seven-row scope or final contribution require the specified instructor/team review.

### Research sequence and claim boundary

- **Phase 1 precedes Phase 2:** pin and test existing tools, measure a real limitation, determine whether it is protocol behavior, tool coverage, or capture conditions, and quantify its effect before choosing a solution. A hypothesis or custom implementation is not itself a confirmed problem.
- **QUIC remains the primary depth dive.** The second depth dive is passive visibility, anchored to the team-reported L2 result: 0 JA4X/JA4H outputs without session secrets versus 5 with secrets (4 JA4X certificate-chain entries plus 1 JA4H) for one TLS 1.3 curl sample. The key log is intentionally absent, so this is imported/team-run evidence and cannot be independently regenerated from this repository. L3 capture-vantage work is secondary and must not replace either depth dive without approval.
- **Approved contribution framing: measured map plus one engineering first step.** The project-specific contribution is designing, implementing, and evaluating the C++ `InitialContextAssociator` for lightweight passive extractors—not inventing stateful CID tracking or changing RFC 9001. It demonstrates the prototype's stateless per-datagram/DCID packet-accounting blindspot (10 curl and 6 Chromium failures), recovers those 16 Initial packets with zero client decrypt failures in the tested captured-order traces, and obtains 5/5 exact ClientHello byte matches per trace against TShark 4.6.4. The wire-order boundary is part of the result (reverse 0/5, shuffle 4/5). Keep each number bounded to the two tested traces and the committed batch; rubric and prior-art review still determine how the course evaluates this engineering/evaluation contribution.
- **A fingerprint describes an observation, not an identity.** JA3/JA4-family constructions are not RFC-defined algorithms; RFCs define the protocol fields. A fingerprint, one MSS/TTL value, or a capture-point difference does not by itself identify a user/application, prove a proxy, or prove attribution error.

### Design-review and viva answers captured as decisions

| Question | Decision / answer | Limit |
|---|---|---|
| Why can a passive observer decrypt a QUIC v1 Initial? | RFC 9001 derives Initial packet-protection keys from public version and original-DCID inputs; this makes Initial contents, including a carried ClientHello, recoverable when the capture is complete and association is correct. | It does not reveal general TLS traffic secrets or 1-RTT/application data. Retry changes the Initial context and remains unsupported here. |
| Why remove QUIC header protection before AEAD decryption? | Header protection obscures fields including packet-number bits. Remove it first, reconstruct the packet number, then use the unprotected header as AEAD associated data and authenticate/decrypt the payload. | Authentication failure is a hard failure, not permission to guess a different key/context. |
| Why are packet boundaries not TLS handshake boundaries? | A UDP datagram may contain coalesced QUIC packets, and CRYPTO frames carry handshake-stream offsets that may span packets. Parse bounded packet/frame lengths, then reassemble CRYPTO by offset before parsing the TLS message. | Do not concatenate CRYPTO data in packet arrival order or treat a datagram as one TLS message. |
| Why use a JA4 reference instead of immediately implementing JA4? | The construction is release-specific and involves filtering, ordering, GREASE, transport markers, and hashes. Reuse a pinned reference first, then validate the QUIC-specific fields and field-level inputs independently. | A matching final hash alone does not validate the field construction; no custom JA4 is currently claimed. |
| What does a fingerprint identify? | At most, a normalized observation of protocol fields on the captured leg and under the selected tool/version. | It is not proof of a user, executable, ultimate origin, proxy, or stable unique identity. |

# Working decisions and rationale

**Updated:** 5 November 2026

**Status:** Provisional repository record. This is not a signed or unanimous team decision; team review, course-rubric review, and approval of the final contribution remain open.

## 1. Use C++20 for the bounded QUIC protocol core; keep experiment orchestration in Python

The project keeps the required QUIC depth dive in a small modular C++20 core: classic-PCAP/UDP adaptation, QUIC v1 long-header parsing, Initial key derivation and packet decryption, supported Initial-frame parsing, offset-aware CRYPTO reassembly, and TLS ClientHello validation. C++20 `std::span`, `std::optional`, and `std::string_view` express borrowed byte ranges and absent/partial parse state without forcing copies at each layer. OpenSSL 3 supplies the cryptographic primitives; the build does not add a libpcap dependency. Python remains the experiment layer for deterministic PCAP mutations, TShark comparison, manifests, and conservative SYN/SYN-ACK summaries.

This is an engineering trade-off, not a novelty claim. It gives the byte parser explicit module boundaries and unit-testable functions, but requires careful bounds checks and adds a compiler/CMake/OpenSSL setup requirement. The current adapter intentionally supports only classic PCAP v2 Ethernet with unfragmented IPv4/IPv6 UDP; PCAPNG, VLANs, IP fragments, IPv6 extension chains, QUIC v2, Retry transitions, tuple migration, 0-RTT, every frame type, and JA4 calculation are outside the implemented scope. The new Initial-context path is a bounded, fixed-4-tuple association model, not a complete connection/migration implementation. C++20, modularity, and RFC Initial decryption alone are not an original contribution.

The WSL verification batch at `results/track2/verification-batch-20261104-201936/` records GCC 15.2.0, OpenSSL 3.5.5, TShark 4.6.4, Linux 6.18.33.2 WSL2, CTest 1/1, and pytest 39/39. The batch is user-run evidence: its manifest hashes and JSON structure were checked in this checkout, but the WSL run was not independently regenerated here. The RFC 9001 Initial key test vector remains a separate unit test from capture-level evidence.

## 2. Keep broad QUIC recovery rejected; test the narrower Initial-context accounting defect

The batch evaluates six cases for each of two captures: baseline, reversed packet-record order, fixed-seed shuffle, one selected Initial-CRYPTO record dropped, every third selected Initial-CRYPTO record dropped, and a selected record truncated by 64 captured bytes. For each client, all six comparisons report exact-byte multiset equality with TShark's ClientHello bytes from that same case: 27/27 reference ClientHellos matched, with 0 misses and 0 extras. The every-third-drop case has 2 references and 2 matches, not recovery of the five original hellos. Aggregated: 54/54 reference outputs matched across 12 run-cases. These are batch-artifact-inspected results from a user-run WSL execution, not independent Arena reproduction or external ground truth; TShark is the comparator, and the comparison is conditioned on what TShark emits from each mutated PCAP.

The extractor's incomplete-flow and Initial decryption-failure statuses must not be conflated with a missed complete ClientHello: the measured comparison found no missing complete TShark output under these tested conditions. The evidence still rejects a broad extraction/reassembly contribution. A narrower packet-accounting defect is measured in the legacy logs: Chromium has 16 client Initial records, 10 successful and 6 failed; curl has 20, 10 successful and 10 failed. The failures lie in five switched-DCID alias buckets per trace, not five lost ClientHellos.

RFC 9001 §5.2 derives Initial secrets from the original client Initial DCID (subject to the Retry transition); the prototype's former per-packet implementation instead keyed each packet using its current DCID. The bounded stateful associator preserves the original DCID on the direction-normalized UDP 4-tuple, learns server Initial SCIDs, and maintains separate client/server packet-number contexts. The committed WSL verification batch `results/track2/verification-batch-20261105-105416/` was run against code commit `fa9fcdb` and is now inspectable in the checkout. It records a clean build, CTest 1/1, pytest 52/52, TShark 4.6.4, the exact baseline byte-multiset comparisons, and per-direction/per-connection accounting.

| Trace | Client Initial packets | Legacy DCID-keyed client decrypted / failed | Switched aliases / client packets using aliases | Stateful client decrypted / failed | Stateful server Initial decrypted / failed | Baseline ClientHello byte match vs TShark |
|---|---:|---:|---:|---:|---:|---:|
| curl | 20 | 10 / 10 | 5 / 10 | 20 / 0 | 5 / 0 | 5/5, multiset equal |
| Chromium | 16 | 10 / 6 | 5 / 6 | 16 / 0 | 5 / 0 | 5/5, multiset equal |

Each trace has five observed 4-tuple associations; baseline context-miss counts are zero in both directions. The measured delta is +10 decrypted curl client Initial packets and +6 Chromium packets. These are packet-accounting changes, not increased ClientHello recall. The baseline TShark byte comparison uses the same captured-order PCAP and matches all five complete ClientHellos in each trace by byte multiset, with zero misses/extras.

The stateful impairment results show an important order-dependence: in each trace, reverse-record-order gives 0/5 matched hellos, and shuffle gives 4/5; baseline, drop-one, every-third-drop, and truncation cases match the TShark outputs for those cases (5/5, 5/5, 2/2, and 5/5 respectively). Therefore “no recall regression” is supported only for the captured-order baseline, not reordered traces. The earlier stateless matrix remains 27/27 per trace across its six cases.

The causal boundary is the prototype's single-pass input-record processing, not QUIC semantics or a TShark failure. The first client Initial observed for a direction-normalized UDP 4-tuple seeds the context's presumed original DCID. A server SCID alias is added only after the corresponding server Initial is observed and associated with a previously observed client SCID. In the reversed-record batch, later client Initials using switched DCIDs occur before that server alias announcement and before the true first client Initial; the first switched DCID is consequently used as the provisional original-DCID context. The parser neither buffers unresolved packets nor reorders by timestamp, so subsequent packets cannot be associated with the required context in this pass. This explains the observed 0/5 reverse result; the fixed-seed shuffle retains enough context for 4/5. A timestamp-aware pre-pass or bounded buffering/deferred association could address this, but neither is implemented. These are tested mutation outcomes, not claims about every out-of-order capture.

Baseline ClientHello recall does not increase: both the earlier stateless path and stateful path emit 5/5 complete ClientHellos on each original-order trace, with exact-byte multiset parity against TShark 4.6.4. The user's supplemental frame audit reports that each complete ClientHello was already wholly present in pre-switch datagrams in these two captures, so the additionally accounted-for packets contain no bytes needed to complete those particular ClientHellos. That frame-level audit is user-reported and not yet archived in the batch; keep it labeled accordingly until packet/frame evidence is committed. The stateful change is packet-level accounting correctness and could protect extraction when handshake bytes span later datagrams, but these traces do not demonstrate a recall increase.

For the same reason, distinguish the prototype's legacy stateless accounting from the reference dissector: the user's separate WSL check reports that `tshark -r <capture> -Y 'quic.long.packet_type == 0 && quic.decryption_failed'` returned zero matching rows on each original curl/Chromium capture, including post-switch DCIDs. The exact filter output is not in the committed batch, so this remains user-reported supplemental evidence. TShark/Wireshark is treated as a stateful reference implementation/comparator, not an independent ground-truth oracle; do not describe the 16 prototype-baseline failures as Wireshark failures.

The academic scope is deliberately narrow. CID mechanics are specified by RFC 9000 §7.2 and Initial-key context by RFC 9001 §5.2; maintaining connection/CID state is established practice in full QUIC implementations and stateful analyzers (for example, [Google QUICHE](https://github.com/google/quiche), [ngtcp2](https://github.com/ngtcp2/ngtcp2), and [Wireshark](https://github.com/wireshark/wireshark)). We do not claim that stateful CID tracking itself is globally novel. The project evaluates a minimal stateless-to-stateful transition for lightweight passive streaming fingerprinting, using a fixed-tuple Initial associator to measure packet-accounting effects and ordering limits. This is a bounded engineering/evaluation contribution proposal, not an established novelty finding; targeted prior-art review and course-rubric/team approval remain open.

Known limitations and future work: Retry remains unsupported (`retry_packets_observed_unsupported`), as do migration/rebinding, QUIC v2, and order-robust deferred association. Future work is to add Retry integrity/key-transition vectors and captures, then test bounded buffering or a timestamp-aware discovery pass for out-of-order records. None of these capabilities should be implied by the current results.

The seven-row artifact audit marks L1/L2/L3/L4/L5/L7 PASS and L6 NOT_MEASURED for public IPv6 egress. The optional local-loopback live check in the committed run itself failed because tcpdump produced no packet-bearing IPv6 PCAP; overall live status is therefore FAIL, while public egress remains unmeasured. The evidence is now archived, but independent Arena reproduction, novelty, course-rubric fit, and team approval remain open. Key citations: `results/track2/verification-batch-20261105-105416/quic-stateful/curl/impairment-results.json`, `results/track2/verification-batch-20261105-105416/quic-stateful/chromium/impairment-results.json`, `results/track2/verification-batch-20261105-105416/seven-rows-live.json`, `results/track2/verification-batch-20261105-105416/make-test.log`, and `results/track2/verification-batch-20261105-105416/environment.txt`; see also `docs/quic/implementation-status.md` and `results/verification-status.md`.

## 3. Treat L3 capture-vantage attribution as a candidate question, not a proxy finding

The earlier TSO/GSO-on/off captures remain separate single-vantage runs: each has three complete streams with client profile MSS/window-scale/window/TTL `1460/10/64240/64` and peer `65495/7/65408/63`. They are not paired and do not establish termination. A later committed user-run batch contains three manual timing-correlated container/Wi-Fi probe pairs to `104.16.124.96:443`; each is classified `separate_tcp_legs_or_sequence_rewrite`, with distinct tuples and initial sequence numbers. Container client MSS/WS/TTL is `1460/10/64` versus Wi-Fi `1460/8/128`; peer SYN-ACK is `1460/7/63` versus `1400/13/52`. MSS 65495 does not occur in this paired run.

The WSL `eth0` capture is 188 bytes with two packets captured but zero parsed SYN rows. vEthernet has 175 packets and eight SYN observations across four unrelated streams, not the controlled target tuple. The bridge capture failed because the named interface did not exist. Wi-Fi is an adapter capture, not a physical-wire tap. These results show a cross-vantage handshake difference for the three controlled requests but do not locate an intermediate mechanism, prove a proxy, calculate JA4T/JA4TS, or show OS misclassification. L3 is secondary, not the active primary candidate. Keep MSS 65495 scoped to the earlier offload captures and see `docs/l3-contribution-plan.md` for pair IDs and provenance.

## 4. Interpret post-switch QUIC DCIDs under the Initial key schedule, not as direction failures

Five later client Initial DCID buckets in each imported QUIC trace use a DCID equal to a server Initial SCID. These are client-to-server records, not server-direction attempts. The baseline stateful run now shows the narrow fix in the prototype's accounting: it decrypts all 20 curl and 16 Chromium client Initial packets with zero failures, while the prior DCID-keyed accounting reports 10/10 and 10/6 success/failure. All five server Initial packets per trace decrypt, and baseline context misses are zero. This aligns the measured packet-key association with RFC 9001 §5.2's original-DCID key derivation for these fixed-tuple captures; it does not establish full RFC 9001 compliance, Retry handling, migration support, or order-independent initialization. See [RFC 9001 §5.2](https://www.rfc-editor.org/rfc/rfc9001.html#section-5.2), [RFC 9000 §7.2](https://www.rfc-editor.org/rfc/rfc9000.html#section-7.2), and `results/track2/verification-batch-20261105-105416/quic-stateful/`.
